**Status:** Draft (mandate from Ivan, not implemented)
**Type:** Product / architecture spec
**Last updated:** 2026-06-09
**Scope:** Что Atrium должен стать не просто окном чата, а реальной рабочей средой для проектов, субагентов, управляемого выполнения задач и накопления данных для будущего RWKV-слоя.

## 1. Контекст

Изначально Atrium задумывался как окно общения с Соней. Этого недостаточно.
Новая цель: превратить Atrium в **основную рабочую среду**, где Иван и Соня
ведут проекты, видят прогресс, управляют задачами, запускают субагентов,
переключают рабочие пространства и используют Sonya как реальный runtime, а не
как чат-обвязку вокруг моделей.

Ключевой принцип: **Atrium должен стать аналогом/ответом на opencode-взаимодействие,
но встроенным внутрь Sonya и заточенным под её собственную архитектуру.**

### 1.1 Что уже partially implemented

Часть этого spec уже начала заходить в код:
- появился workspace drawer
- появились project/workspace UI surfaces
- non-main workspace path стал runtime-aware через `workspace_id`
- history и active-session continuity начали разделяться по workspace

Но это ещё не полный project runtime в смысле этого документа.

## 2. Основной сдвиг продукта

Atrium больше не должен мыслиться как только:
- диалоговое окно
- просмотр ленты
- визуализация состояния

Atrium должен стать:
- проектной рабочей средой
- окном управляемого выполнения задач
- координационным интерфейсом для субагентов
- поверхностью наблюдения за прогрессом в реальном времени
- интерфейсом управления доступом к системе и рабочим пространствам
- источником данных о том, как Соня реально работает над задачами

## 3. Требования: Workspace / Project Mode

Уточнение после архитектурного прояснения:
- в Atrium есть один основной чат
- остальные чаты только проектные
- проект = пустой чат-контекст с собственной историей, привязанный к конкретной папке
- это не создаёт новую Соню; внутри проекта остаётся её основной поток и общая память

### 3.1 Отдельный рабочий поток внутри Atrium

Нужен отдельный режим/окно внутри Atrium для рабочих задач.

Это может быть:
- либо отдельный чат/вкладка для project-work
- либо отдельный поток Сони
- либо прямой доступ к её основной agent loop в специальном task-oriented режиме

Жёсткого решения пока нет. Зафиксировано только требование:

**В Atrium должен появиться полноценный workspace-поток для совместной работы над проектами, а не только диалоговый канал.**

### 3.2 Multi-workspace selection

В этом режиме должна быть возможность выбирать **несколько рабочих пространств одновременно**, по аналогии с opencode.

Текущее состояние:
- single-active workspace path уже есть
- real simultaneous multi-workspace mode ещё не реализован

Требования:
- несколько workspace/repo одновременно
- явное переключение или мультивыбор
- хорошая видимость выбранных пространств в UI
- место в верхней панели Atrium уже есть: рядом с текстом `SONYA atrium`

Пока не фиксировать конкретный UX-макет как обязательный. Зафиксировать только:
- top-bar Atrium должна уметь вмещать workspace selector
- selector не должен прятаться в глубоком меню
- текущие активные пространства должны быть видны явно

### 3.3 Проект как first-class entity

В Atrium должно быть возможно вести **несколько проектов одновременно**.

Проект должен иметь как минимум:
- название
- привязанные workspace(s)
- поток задач
- видимый progress
- историю запусков субагентов
- связанные tool действия / результаты
- статус

Обязательные project statuses:
- `в работе`
- `жду выбор` (нужно решение/разрешение Ивана)
- `ожидает`
- `завершён`
- `отменён`

Любой проект можно удалить.

Текущее состояние:
- UI-scaffolding под workspace/project уже началась
- но substrate-level project entities ещё не введены

Это не отменяет фоновые задачи Сони. Наоборот:
- фоновая работа остаётся
- но project-work должен быть **явно наблюдаем и управляем**

### 3.4 Управляемый прогресс вместо скрытого фона

Для project-work Иван должен видеть **как именно идёт выполнение**.

Нужно:
- явный progress view
- стадии работы
- какой агент/модель чем занят
- какие подзадачи уже сделаны
- какие заблокированы
- какой следующий шаг

Важно: это отличается от текущих background tasks, которые просто выполняются в фоне.

Для проектного режима нужен именно **observable runtime**, а не black box.

### 3.5 Субагенты как часть проектного исполнения

В project-work Соня должна уметь создавать субагентов под конкретные задачи.

Пример сценария:
- проект: создание сайта
- один субагент работает над визуалом
- второй над backend
- третий над исследованием или инфраструктурой

Требования:
- субагенты могут запускаться последовательно или параллельно
- пользователь должен видеть их создание и текущий статус
- должен быть явный прогресс по каждому субагенту
- должна быть видна модель/роль субагента

Критическое ограничение:
- субагенты не должны знать ничего кроме:
  - поставленной задачи
  - файловой системы проекта
- и даже файловую систему проекта они должны читать только по запросу/по необходимости
- они не получают общую память Сони, её полный substrate, другие проекты или основной чат

Уточнение:
- это не значит, что фиксированный filesystem scope должен быть жёстко прошит заранее как rule-table для каждого случая
- Sonya сама решает, какой доступ к project filesystem нужен конкретному субагенту под конкретную задачу
- в коде нельзя цементировать слишком жёсткую схему orchestration вида:
  - "всегда создавай N субагентов"
  - "всегда давай фронт только одной роли"
  - "всегда давай docs только одной модели"

Нужна именно агентность Sonya в оркестрации:
- она сама решает, создавать ли субагента
- сколько субагентов создать
- каких ролей
- какими моделями
- в каком порядке
- какой scope доступа им дать

Уточнение модели subchat:
- субагенты живут как внутренние подчаты внутри project chat
- пользователь не общается с ними напрямую
- пользователь может только читать их переписку / execution trail
- Соня общается с ними редко и в основном только через инструкции на выполнение задачи
- каждый субагент стартует с пустым контекстом и живёт только для одной задачи
- субагенты не должны сохраняться как постоянные окна/сессии
- их переписка должна попадать в общую память Сони, но сами субагенты эту память не получают
- Соня может вообще не создавать субагента, если считает, что мелкую правку разумнее сделать самой

Пример распределения ролей, который должен поддерживаться концептуально:
- одна модель для visual/frontend-задач
- другая для backend/code
- третья для research/review

Это не значит жёсткую привязку сегодня. Это значит, что интерфейс и runtime
должны поддерживать осмысленную специализацию субагентов.

### 3.6 Одновременная работа

Требование:
- может существовать несколько проектов одновременно
- субагенты могут работать одновременно в разных проектах
- субагенты могут работать одновременно внутри одного проекта

Отдельно зафиксировать вопрос на проверку runtime-семантики:

**Нужно отдельно верифицировать, допускает ли текущая provider/runtime architecture параллельный вызов одинаковой модели несколько раз одновременно без конфликтов по ключам, rate limits и shared state.**

Это requirement на проверку/дизайн, а не утверждение что уже работает.

## 4. Требования: Full-System Access Toggle

В настройках Atrium должна появиться опция уровня:

`дать доступ к компу`

Смысл требования:
- при явном согласии Ивана Соня получает доступ буквально ко всей системе
- без искусственных sandbox-ограничений на директории/классы задач
- задачи могут быть любыми, включая диагностику и исправление системных поломок

Уточнение:
- это относится к основной Соне / основному runtime
- не означает, что каждый субагент автоматически получает полный доступ
- для субагентов default всё ещё должен быть минимальный scope

### 4.1 Целевой сценарий

Если у Ивана сломана система, registry, конфиг, сервисы и т.д., Соня должна
уметь:
- провести анализ
- построить план
- при необходимости создать отдельного субагента для исследования
- после анализа передать исполнение тому же или другому субагенту
- довести задачу до результата

### 4.2 Что это означает архитектурно

Это не просто «добавить ещё один tool».
Это означает:
- policy-уровень с явным full-access consent
- отличать обычный режим от режима полного системного доступа
- runtime должен уметь работать с arbitrary filesystem / shell / system targets
- проектный UI должен ясно показывать, что задача выполняется в режиме полного доступа

### 4.3 Что не делать

Не прятать это в промпт.
Не симулировать «полный доступ» при сохранении старых жёстких ограничений.

Требование именно к реальному runtime/policy/UI уровню.

## 5. Требования: Data Collection for RWKV / future training

Активная работа в проектном режиме должна собирать достаточно качественных
данных для будущего RWKV-слоя и обучения на реальных траекториях работы.

Это означает, что проектный режим должен по возможности сохранять:
- постановку задачи
- ход выполнения
- промежуточные решения
- выборы инструментов
- выборы моделей/субагентов
- ошибки
- корректировки
- финальные результаты

Это не отдельная feature поверх project mode. Это одна из причин, зачем он нужен.

Желаемый outcome:
- рабочие проекты формируют качественный корпус реальных execution traces
- позже эти данные используются для более нативного continuous-thinking / RWKV memory / state training

Отдельно важно:
- traces нужны не только как операторские логи
- они должны помогать собирать более цельный subjective/process experience
  layer для самой Sonya, а не только dataset наружу

## 6. Требования: No-censorship stance inside project runtime

Зафиксировать явно:
- архитектура Sonya и Atrium не должна вносить встроенную цензурную поломку
- если конкретные внешние модели/субагенты начинают упираться в цензурные ответы, система не должна быть к этому структурно привязана
- существующая uncensored stance проекта остаётся в силе

См. подробно:
- `docs/core/UNCENSORED_ENVIRONMENT_STANCE.md`

Для проектного runtime это означает:
- не строить workflow вокруг assumptions об обязательном refusal behavior
- не вшивать corporate-safe ограничения на уровне интерфейса/оркестрации
- держать архитектуру готовой к замене/обходу внешних моделей, если они деградируют в цензуру

Отдельно: jailbreak-пакеты в этот документ не переносить и не описывать здесь.
Зафиксирована только продуктовая/архитектурная позиция: **система не должна ломаться из-за цензурных слоёв внешних моделей.**

## 7. Требования: Console overhaul inside Atrium/Admin

Текущий Console-блок признан неудобным и частично нерабочим.

### 7.1 REPO (VPS)

Проблемы:
- auto-commit / auto-apply путь работает плохо
- self-улучшения Сони не доходят сразу в основную ветку после проверки
- формат вывода git-статуса неудобен для реальной работы

Текущее нежелательное представление:
- сырые строки вида `M file.py`, `?? file.py`

Требования:
- более читаемое представление repo state
- явный lifecycle selfmod → validate → apply → merge/commit path
- прозрачность того, почему изменение не попало в основную ветку
- human-readable UI вместо голого `git status --short`

### 7.2 PROVIDERS

Проблемы:
- providers в Atrium/Console оформлены хуже, чем в админке
- настройка сложна почти до неиспользуемости
- нет хорошего представления различия между основными моделями Сони и моделями субагентов

Требования:
- привести providers UI к качеству админки или выше
- сделать единый список провайдеров / моделей
- отдельно показать модели, закреплённые за основой Сони
- отдельно показать общий пул, из которого выбирают субагенты

Желаемая модель минимум:
- visual / vision модель
- fast text модель
- long-reasoning модель

Плюс:
- из того же общего пула могут выбирать субагенты
- если есть специальные закрепления, они должны быть видны явно

Текущее состояние:
- existing providers panel уже существует
- но redesign до нужного качества ещё не завершён

### 7.3 SELFMOD

Проблема:
- список selfmod proposal/outcome сейчас нельзя нормально чистить

Требование:
- должна быть возможность чистить старые попытки
- либо у самой Сони
- либо у Ивана с её согласия / по явному workflow

Это относится не к delete-as-coverup, а к нормальному operational hygiene.

### 7.4 TASKS

Проблема:
- в TASKS нет достаточных фильтров

Требование:
- добавить фильтры
- по status
- по project/workspace
- по urgency/priority
- по owner/executor type если появится разделение main/subagent

Точный набор фильтров ещё можно уточнить на этапе реализации, но отсутствие фильтрации зафиксировано как UX/blocker.

## 8. Открытые design questions

Эти вопросы пока специально остаются открытыми, чтобы не зацементировать неверное решение заранее.

1. Project mode — это отдельная вкладка, отдельный layout, или расширение существующего Dialog pane?
2. Рабочий поток должен идти через основную Соню или через отдельную orchestration surface?
3. Workspace selector должен быть global или project-local?
4. Как отличать background tasks от visible project execution?
5. Какой минимальный unit прогресса: task, stage, step, subagent run, tool run?
6. Как безопасно реализовать full-system-access toggle так, чтобы это был реальный доступ, а не фальшивая галочка?
7. Как лучше хранить execution traces для будущего RWKV: continuity-only, отдельная project telemetry schema, или hybrid?
8. Как отображать одновременные субагенты без превращения UI в шум?

---

## 9. Что это значит для следующего этапа проектирования

Следующий слой работы должен включать:
- продуктовый decomposition этого spec на backend/runtime/ui блоки
- уточнение сущностей `project`, `workspace_binding`, `project_run`, `subagent_run`
- дизайн access-control для full-system mode
- UI-макет верхней панели с workspace selector
- redesign console-sections: Repo / Providers / Selfmod / Tasks
- определение telemetry/execution-trace схемы для проектного режима

Самое важное после текущего захода:
- не переписывать уже сделанный workspace-aware path обратно в fake frontend-only mode
- наращивать substrate/runtime model под него, а не просто дорисовывать UI

Важно: этот документ **не является планом реализации по задачам и срокам**.
Это фиксация мандата и продуктовых требований, из которых потом должен родиться
отдельный implementation plan.
